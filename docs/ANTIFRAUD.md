# Антифрод: предложение

Служебная записка для обсуждения. Касается схем «свой–чужой»: накрутка поездок между
знакомыми, дробление заказов, быстрые отмены после назначения, «резиновые» рейтинги.

## 1. Опора на то, что уже есть

Текущая схема уже даёт сильные идентификаторы:

- **Вход по MAX miniapp с подтверждённым телефоном** — почти анонимных аккаунтов нет.
- `User(max_user_id)` → `Client` / `Executor` (есть `rating_percent`, `status`,
  таблица `ExecutorSuspension` — уже используется администратором для отстранений).
- `Order(client_id, executor_id, status, total_price, ...)`, журнал `OrderEvent`.
- `Rating` (лайк/дислайк пары клиент→исполнитель), `OrderExtra`, `ExecutorWorkSession`.

Не хватает одного: **привязки аккаунта к устройству** и **журнала подозрительных
сигналов** с ручной очередью на проверку.

## 2. Что добавить (MVP)

### 2.1. Таблица `device_session`

| поле | смысл |
|---|---|
| `id`, `user_max_id`, `role` | кто сел |
| `device_id` | uuid, генерируется в localStorage миниаппа; в MAX — дополнительно hash из WebApp initData, если доступен |
| `ip_hash` | `sha256(ip + SERVER_SECRET)` — сам IP не храним |
| `ua_hash` | hash user-agent (браузер/версия/платформа) |
| `first_seen`, `last_seen` | окно жизни |

Запись при каждом успешном входе (`/auth/max/miniapp`) и обновление `last_seen`
на каждом summary. Через две недели старые сессии чистятся.

### 2.2. Таблица `fraud_signal`

`id, order_id, pair_key ("client:executor" или "client:"), code, weight, meta(json), created_at`.

### 2.3. Таблица `fraud_review`

`id, pair_key, risk_score, status, resolver_operator_id, resolved_at, comment, allowlisted`.

Статусы: `open → review → under_review → confirmed | false_positive`.

## 3. Сигналы и веса (v1)

| код | условие | вес |
|---|---|---|
| `same_device_pair` | клиент и исполнитель входили с одного `device_id` | +45 |
| `frequent_pair` | ≥5 совместных заказов за 7 дней у клиента, у которого всего ≤10 заказов | +25 |
| `shared_ip_cluster` | с одного `ip_hash` за неделю заходили ≥3 разные аккаунты-клиенты | +20 |
| `rapid_roundtrip` | отмена/завершение <3 мин и повторный заказ той же парой в течение часа | +20 |
| `cancel_after_assign` | клиент отменяет после назначения ≥3 раза за 24 ч | +15 |
| `collusion_rating` | клиент ставит лайк одному исполнителю ≥5 раз за месяц | +15 |
| `price_outlier` | сумма заказа > медианы по такому же маршруту/тарифу ×2.5 | +15 |
| `night_cluster` | ≥5 заказов у пары в 00:00–05:00 за неделю | +10 |
| `cold_pair_big_price` | первый заказ пары на сумму > 3000 ₽ | +10 |

`risk_score = min(100, Σ веса активных сигналов пары за 30 дней)`.

Скор считается на событиях: завершение/отмена заказа, новый отзыв, новая
device-сессия, новая заявка в поиск. Агрегат пишется в `fraud_review.risk_score`.

## 4. Пороги и действия

| диапазон | статус | что происходит |
|---|---|---|
| 0–29 | OK | ничего, только журнал сигналов |
| 30–59 | `review` | карточка пары в очереди оператора; заказы продолжают идти как обычно |
| 60+ | `under_review` | новые заказы этой пары **не назначаются автоматически** (исполнитель не получает их в ленту, клиент видит «ищем исполнителя» дольше); остаётся ручной поиск у оператора |

Автоматических банов нет — всегда решение человека.

## 5. Ручные резолюты (оператор/админ)

Очередь в админке: `GET /api/admin/fraud/queue` (пары с status != confirmed/false_positive),
решение: `POST /api/admin/fraud/{id}/resolve {action, comment}`.

- `confirm_fraud`: клиенту — запрет новых заказов (блокировка), исполнителю —
  `ExecutorSuspension` (таблица уже есть) с причиной «фрод, решение оператора»;
  история пары остаётся.
- `false_positive`: снять флаг, обнулить скор пары, опционально `allowlisted`
  (например, семья/компания — помечается один раз и больше не беспокоит).
- `escalate`: передать админу (если в админке появится уровень выше оператора).

Каждое решение фиксируется: кто, когда, комментарий. Журнал сигналов не стирается.

## 6. Экспорт и отчётность

- Еженедельная выгрузка подтверждённых фрод-пар (CSV в админке — как существующий
  `/admin/orders/export.csv`).
- Счётчики на дашборде оператора: сколько пар в review, сколько поднялось за неделю.

## 7. Оценка MVP

| работа | время |
|---|---|
| схема + запись device-сессий (backend + обе миниаппы передают device_id) | ~4 ч |
| генерация сигналов на событиях + расчёт скор | ~4 ч |
| очередь и резолюты в админке | ~5 ч |
| тесты и прогон на проде | ~2 ч |
| **итого** | **~1.5–2 дня** |

## 8. Чего в MVP не делаем

- ML-модели и «поведенческие» скоринги (нужна накопленная история).
- Автобаны без оператора.
- Скоринг по гео-траекториям (следующий этап — когда появятся нормальные треки).
