# Промты для доведения «Про» до релиза

Промты рассчитаны на слабые и бесплатные модели. Правила работы:

- Одна задача — одна сессия модели. В начало каждой сессии вставляйте блок «Общий контекст», затем текст задачи.
- Выполняйте промты по порядку: последующие опираются на результат предыдущих.
- После каждой задачи проверьте результат (`git diff`, сборка, тест) и только потом коммитьте.
- Деплой и `git push` делает владелец, а не модель.

## Часть 1. Жизненный цикл заказа (делать первой)

### Что есть сейчас (проверено по коду 02.11.2026)

Статусы: `created`, `chain_reserved`, `assigned`, `accepted`, `in_progress`, `completed`, `cancelled`.

Переходы разбросаны по трём местам и дублируют друг друга:

| Переход | Где | Проблема |
|---|---|---|
| created → assigned | `main.py` `POST /api/orders/{id}/assign/{executor_id}` (~стр. 795) | **Нет авторизации**: назначить можно любой заказ на любого исполнителя. Вызывают и исполнитель (App.jsx `accept`), и админка |
| assigned → accepted | `routers/order_chain.py` `POST /orders/{id}/accept?executor_id=` (~стр. 112) | **Нет авторизации**, executor_id берётся из query |
| accepted → in_progress | `routers/order_chain.py` `POST /orders/{id}/start?executor_id=` (~стр. 135) | **Нет авторизации** |
| → completed | `main.py` `POST /api/orders/{id}/complete` (~стр. 935) | **Нет авторизации**: кто угодно завершает чужой заказ и начисляет деньги на баланс. Завершает даже из `assigned`, минуя поездку |
| accept/start/complete | `main.py` `POST /api/orders/{id}/executor-action` (~стр. 1634) | Второй вариант тех же переходов: принимает сразу из `created` в `accepted`, не пишет OrderEvent, комиссию пересчитывает по текущей настройке. Без события `completed` ломаются часовое окно оценки, «Оставили вещи» и чат после поездки (`_completed_at`). Вызывают его только `executor/src/AvailableOrders.jsx` и `executor/src/Summary.jsx`, а эти файлы нигде не импортируются, то есть это мёртвый код |
| → cancelled | `main.py` `POST /api/orders/{id}/cancel` (~стр. 1585) | Отменяет только клиент. Не пишет OrderEvent и причину. Исполнитель отказаться от принятого заказа не может |
| created → cancelled | `_order_timeout_watcher` (`main.py` ~стр. 2895) | Через 5 минут отменяет **и предзаказы** (`scheduled_at`): эвакуация, которая доступна только как предзаказ, закрывается сама |
| время ожидания | `main.py` `POST /api/orders/{id}/waiting?minutes=` (~стр. 715) | Без авторизации, минуты присылает клиентская сторона, UI не использует |

Ещё пробелы:
- Нет статуса «исполнитель на месте». Клиенту неизвестно, когда выходить, а платное ожидание считать не от чего.
- Если оператор назначил заказ (`assigned`), а исполнитель не реагирует, заказ висит бесконечно.
- Автотестов в backend нет.

### Целевая схема (допущения — подтвердите или поправьте до старта)

```
created ──исполнитель взял из ленты──> accepted
created ──оператор назначил──> assigned ──исполнитель принял──> accepted
assigned ──отказ или 60 с без ответа──> created (executor_id = null, засчитать пропуск)
accepted ──«Я на месте»──> arrived ──«Начать поездку»──> in_progress ──«Завершить»──> completed
accepted, arrived ──исполнитель отказался (с причиной)──> created (вернуть в ленту)
created, assigned, accepted, arrived ──клиент отменил (с причиной)──> cancelled
любой активный ──оператор/админ отменил──> cancelled
created (не предзаказ) ──5 мин без исполнителя──> cancelled
chain_reserved ──предыдущий заказ завершён──> assigned
```

Платное ожидание: первые 3 минуты от `arrived` бесплатно, дальше — по `pricing.calc_waiting`. Сервер считает его сам при переходе `arrived → in_progress`.

## Часть 3. Белые списки и плохой мобильный интернет

При включённых белых списках мобильный интернет пропускает только одобренные сервисы. Домен procityservice.ru в этот список не входит, поэтому миниапп, API и тайлы карты недоступны. Обфускация APK, смена IP или Cloudflare здесь не помогают. Пропускать будут только сервисы из списка. Мессенджер MAX в нём, поэтому сообщения бота доходят. Это единственный канал, который можно сделать запасным без участия властей.

Нетехнические задачи владельца:
- Узнать актуальный порядок включения сервиса в белый список (Минцифры, региональные власти) и подать заявку. Сервис перевозок с локальной регистрацией и хостингом в РФ — аргумент в пользу включения.
- Проверить, у какого провайдера стоит VPS 5.35.126.190 и где физически находится сервер.

### W1. Запасной заказ через чат-бота MAX

```
Цель: когда миниапп не открывается, клиент может заказать такси прямо в чате бота.
Сообщения идут через серверы MAX, а их белые списки пропускают.

Прочитай backend/app/routers/maxhook.py: там уже принимается геопозиция из чата
(вебхук /webhook/{bot}) и есть subscribe_webhooks.

1) какие сообщения и вложения уже обрабатываются (геопозиция, текст, контакт);
2) диалог: «Отправьте точку подачи» -> геопозиция -> «Куда едем?» -> текст адреса или
   вторая геопозиция -> цена -> «Подтвердить» -> заказ через _create_order_internal;
3) где хранить состояние диалога (таблицы для этого нет — предложи вариант);
```
