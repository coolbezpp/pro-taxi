## 2. КРИТИЧЕСКИЕ ПРОБЛЕМЫ И РЕШЕНИЯ

### 2.1 GPS-трекинг в MAX (iOS/webview)

**Проблема:** MAX на iOS/Android webview блокирует доступ к геолокации браузером.

**Текущее решение:** Нативное APK «Про GPS» (Android) + PWA в системном браузере (iOS).

**Статус реализации:**
- ✅ Android APK собран, deep link `procityservice-gps://track?code=XXX` работает
- ✅ Миниапп распознаёт Android и предлагает APK (баннер + ссылка на `/executor/app/pro-gps.apk`)
- ✅ iOS fallback на PWA (`/executor/track.html`) + `window.open()` в системный браузер
- ⚠️ **Проблема:** PWA на iOS требует ручного переключения между MAX и Safari
- ⚠️ **Проблема:** Пользователь может забыть вернуться, или MAX kill процесс

**План решения (MVP → v2):**
1. **Immediate (текущее):** Оставить как есть; документировать в Help / tutorial
2. **v2:** Использовать `window.location.href` вместо `window.open()` (более надёжно на webview)
3. **v2+:** Попросить у MAX API более открытый доступ к geolocation (лоббирование)
4. **Backup:** iOS native app (если фокус на iOS пользователях)

**Риск:** iOS пользователи могут выключить трекинг, считая его неудобным.

### 2.2 Жизненный цикл заказа

**Проблема:** Неполная реализация переходов между статусами.

**Текущие статусы в БД:**
```
created → assigned → accepted → in_progress → completed
           ↓ (отказ)
        cancelled
```

**Что не реализовано:**
- ❌ Поле `accepted_at` (когда исполнитель нажал «принять»)
- ❌ Поле `arrived_at` (когда исполнитель приехал к клиенту)
- ❌ Переход `assigned → accepted` не принудителен (исполнитель может сразу `accepted → in_progress`)
- ❌ Таймер отказа исполнителя от назначенного заказа (сейчас может бесконечно долго думать)
- ❌ Автоматический откат `accepted → created` если исполнитель не стартовал за N минут

**Последствия:**
- Диспетчер не видит, когда исполнитель реально начал ехать
- Нет данных о времени отклика (для оптимизации матчинга)
- Потеря информации для аналитики (сколько времени от назначения до прибытия)

**План реализации:**

**Этап 1 (URGENT — неделя):** Добавить поля и переходы
```python
# models.py
Order:
  - accepted_at: DateTime (null)  # когда исполнитель нажал «принять»
  - arrived_at: DateTime (null)   # когда исполнитель прибыл к клиенту
  - started_at: DateTime (null)   # когда начался в пути (in_progress)

# Переходы в main.py
POST /api/orders/{id}/accept         → status: assigned → accepted, accepted_at = now()
POST /api/orders/{id}/start          → status: accepted → in_progress, started_at = now()
POST /api/orders/{id}/arrived        → status: in_progress, arrived_at = now() [новый эндпоинт]
POST /api/orders/{id}/complete       → status: in_progress → completed, completed_at = now()
```

**Этап 2 (неделя):** UI в миниапп исполнителя
- Кнопка «Принял» вместо текущей сложной логики
- Кнопка «Приехал» перед завершением
- Таймер отклика: если не принял за 30 сек → вернуть в очередь

**Этап 3 (2 дня):** Аналитика и оптимизация
- Dashboard в админке: avg time назначение→прибытие
- Данные для ML матчинга (какие исполнители быстрее приезжают)

### 2.3 Белые списки (блокировка по IP / IMEI)

**Проблема:** После включения белых списков властями сервис перестаёт работать.

**Причины:**
1. **IP-блокировка:** Сервер VPS заблокирован целиком → миниапп не может подключиться
   - Решение: Использовать CDN / DDoS protection с обходом (CloudFlare, Mimecast)
   - Резервный API endpoint на другом IP / домене

2. **IMEI / Device ID блокировка:** Android приложение распознаётся и блокируется
   - Решение: APK обфускация (ProGuard / R8) + code signing certificate
   - Генерация новых сертификатов при необходимости

3. **Deep link блокировка:** `procityservice-gps://` URI заблокирован на уровне OS
   - Решение: Использовать альтернативные схемы + fallback на веб-сессию

**План реализации (2 недели):**

**Фаза 1 (критичная):** Инфраструктура
- [ ] Подготовить резервный домен на другом регионе
- [ ] Настроить Cloudflare / Akamai для обхода IP-блокировок
- [ ] Документировать процедуру быстрого переключения

**Фаза 2:** Обфускация APK
```bash
# build.ps1: добавить obfuscation
dx --dex --min-sdk-version=26 \
   --obfuscate-attributes=runtime-visible-annotations \
   --output=classes.dex ...
```

**Фаза 3:** Динамические deep links
```java
// MainActivity.java: генерировать случайный suffix
String scheme = "procityservice-gps" + System.currentTimeMillis() % 100;
// или хранить в конфигурации, скачиваемой с сервера
```

**Фаза 4:** Web-first fallback
- Если APK заблокирован → перейти на страницу трекинга в браузере
- Страница работает и без deep links

## 3. АРХИТЕКТУРНЫЕ ПРОБЛЕМЫ И ВОЗМОЖНОСТИ

### 3.1 Масштабируемость

**Текущая архитектура:** One-box (все на одном сервере)
- ✅ Подходит для MVP (< 10k DAU)
- ⚠️ SPOF (Single Point of Failure)
- ⚠️ Нет горизонтального масштабирования

**План (когда понадобится):**
- [ ] Отделить БД (Managed PostgreSQL в облаке)
- [ ] API за load balancer (несколько инстансов)
- [ ] Redis для сессий и кэша
- [ ] Асинхронные очереди (Celery/RQ) для тяжёлых операций

### 3.2 Безопасность

**Текущее состояние:**
- ✅ HTTPS (Caddy с auto-renew Let's Encrypt)
- ✅ Токены (JWT с exp)
- ✅ Базовая аутентификация (phone + code)
- ⚠️ Нет rate limiting
- ⚠️ Нет CORS (open для всех origin)
- ⚠️ API keys не обфусцированы в APK

**План:**
- [ ] Rate limiting (per IP, per user)
- [ ] CORS restrictions
- [ ] Secrets management (environment variables vs hardcode)
- [ ] Security headers (CSP, HSTS, X-Frame-Options)

### 3.3 Мониторинг и логирование

**Текущее состояние:**
- ✅ Docker logs (stdout)
- ✅ API /health endpoint
- ⚠️ Нет centralized logging
- ⚠️ Нет alerts
- ⚠️ Нет metrics (Prometheus)

**План:**
- [ ] ELK Stack (Elasticsearch + Logstash + Kibana) или Loki
- [ ] Prometheus для метрик
- [ ] Alert rules (Alertmanager)
- [ ] Dashboard (Grafana)
